# LH001-91 dual-chip FIFO acquisition over SPI (STM32H750)

Two LH001-91 ADCs (master on CS1/PA4, slave on CS2/PA1) are driven from a single SPI1 master in FIFO mode. The driver (`LH001_91.c/.h`) provides register access, FIFO burst reads, and per-subsystem init; the application (`main.c`) configures both chips, dumps registers over UART for bring-up, then enters a flag-driven loop that reads 25 six-byte frames from each chip on a GPIO interrupt and stages them into a 300-byte double buffer for UART transmit. All SPI traffic is byte-at-a-time polled `HAL_SPI_TransmitReceive`; no DMA is used anywhere in the project, so the H7 D-cache coherency class of bug does not apply here.

**Watch for:** the acquisition trigger appears to be wired to the wrong signal — the driver enables the chip's ENOUGH (FIFO threshold) interrupt but the application only services `DRDY1` and leaves both `INT1`/`INT2` handlers empty (**likely**, needs schematic confirmation); the `ENOUGHTINT` status flag is never cleared after a burst, which on a level-asserted interrupt output stops acquisition after the first burst given falling-edge EXTI config (**likely**); a short burst still copies a full 150-byte block, silently padding the data stream with zeros (**confirmed**); the double-buffer producer/consumer indices desynchronize on the error path and on overrun, so the in-flight UART buffer can be overwritten mid-transmission (**confirmed**); and every SPI byte returns `0xFF` indistinguishably from real data on timeout (**confirmed**).

## High-level view

The ISR/main-loop split is correct, and this is the part of the code most likely to be wrong in hand-written firmware. The EXTI handler only increments a counter and sets a flag, all SPI work happens in the main loop, and every variable crossing that boundary is `volatile` with a single writer. No critical section is required and none is missing.

The FIFO trigger path is where the design does not hold together. `lh001_91_fifo_setup_dual` enables the chip's ENOUGH interrupt in `INTOEN` and disables `DRDY`, but the application's only active EXTI handler is `DRDY1` (PB15), while the `INT1` (PB2) and `INT2` (PB1) handlers are enabled in NVIC and left empty. If ENOUGH is routed to the INT pins as the register naming implies, the burst read is triggered by the wrong edge at the wrong rate, and the FIFO status flag that gates further interrupts is never cleared. This needs resolving against the schematic before anything downstream can be trusted.

The FIFO burst reader is bounds-safe and its frame decode arithmetic is correct, but it reports partial results as success. A burst that terminates early on a tail marker sets `count` below the requested 25 and still returns `LH001_91_FIFO_READ_OK`; the application checks status and master/slave count equality but never that the count equals the threshold, then copies a fixed 150 bytes regardless. The tail bytes are zeros from the `memset`, so short bursts inject silent zero padding into the acquisition stream. The `NO_TAIL` status the enum defines is never assigned by any code path.

The double buffer breaks under both of the conditions it exists to handle. The producer sets `Data_Ready_Flag` without checking whether the previous block was consumed, so a slow consumer loses a block with no overrun counter; and `Write_Index` advances only on the success path while `Read_Index` advances unconditionally at transmit start, so any read error permanently offsets the two and the consumer begins transmitting the buffer the producer is actively writing. `HAL_UART_Transmit_IT`'s return is unchecked, and a `HAL_BUSY` there latches `Uart_Tx_Busy` at 1 forever because no completion callback will arrive.

Error reporting is absent throughout the driver's API surface. Every register access, init, and command function returns `void`, and the SPI port layer converts a timeout into the data value `0xFF`, so a failed bus transaction is indistinguishable from a legitimate register read and propagates into configuration and sample data unnoticed. This is the single change with the widest reach across the codebase.

The register-level code is largely correct: read-modify-write is applied where it matters, masks and positions match the header definitions, and the sign extension in `lh001_91_adc_code2mv` is right. The defects are narrower — a one-bit mask overlap in an unused `reserved1` field, a hardcoded PGA gain of 6 in the millivolt conversion, unvalidated `thresh_num`, and raw magic opcodes in `lh001_91_hw_reset` duplicating constants the header already defines.

## FIFO trigger: ENOUGH enabled, DRDY serviced

`lh001_91_fifo_setup_dual` configures the chip to interrupt on FIFO threshold:

```c
lh001_91_read_regs_dual(chip_id, ADDR_LH001_91_INTOEN, &val, 1);
val &= ~MSK_LH001_91_INTOEN_INTEN;      /* clears DRDY, ENOUGH, FULL, OVERFLOW */
val |= MSK_LH001_91_INTOEN_ENOUGH;      /* enables ENOUGH only */
lh001_91_write_regs_dual(chip_id, ADDR_LH001_91_INTOEN, &val, 1);
```

`MSK_LH001_91_INTOEN_INTEN` is `0x0F`, so this clears the `DRDY` enable at bit 0 and leaves only `ENOUGH` at bit 1. The application triggers exclusively on `DRDY1_Pin` (PB15) in `HAL_GPIO_EXTI_Callback`, and the `INT1_Pin` (PB2) and `INT2_Pin` (PB1) branches are empty bodies with only comments. Both of those EXTI lines are enabled in NVIC in `MX_GPIO_Init`.

The register naming (`INTEN` low nibble, `INTBEN` high nibble) and the pin naming (`INT1`/`INT2` vs `DRDY1`/`DRDY2`) together imply ENOUGH is asserted on the INT pins, not the DRDY pins. If that holds, the burst is triggered by whatever still drives DRDY1 rather than by the threshold event, and at the configured 1 kHz data rate that is roughly a per-conversion edge — so the loop would attempt a 25-frame read per sample, most frames would come back with the EMPTY tail marker, and `fifo_error_count` and `fifo_recovery_count` would climb continuously. Meanwhile the real threshold event on INT1/INT2 is acknowledged by the NVIC and discarded.

This is the one finding I could not confirm from the code: it depends on which chip output each MCU pin is physically wired to, which is not in the repository. Everything else in the FIFO path is downstream of resolving it.

## `FIFOSTA` status flags are never read back

`FIFOSTA` bit 5 (`MSK_LH001_91_FIFOSTA_ENOUGHTINT`), bit 6 (`FULL`) and bit 7 (`OVERFLOW`) are defined in the header and read once during bring-up, but no code path reads or clears them during acquisition. `lh001_91_fifo_setup_dual` read-modify-writes `FIFOSTA` to set the threshold count and preserves whatever those upper bits held; the burst reader and `fifo_recover` never touch the register.

Both EXTI groups are configured `GPIO_MODE_IT_FALLING` in `MX_GPIO_Init`. If the chip's interrupt output is level-asserted until the status flag is cleared — the usual convention for a threshold flag with a dedicated status bit — then the first burst produces one falling edge, the flag stays set, the line stays asserted, and no second falling edge is ever generated. Acquisition stops after one burst and the failure looks like a dead interrupt rather than a protocol error. Clearing `FIFOSTA` per burst would also make the `FULL` and `OVERFLOW` bits usable as a chip-side overrun signal, which is currently unused.

## Burst read reports partial results as success

`lh001_91_read_fifo_burst_dual_num` is bounds-safe: it rejects `expected_count == 0` and `expected_count > LH001_91_FIFO_MAX_DEPTH`, so `frames[i]` stays inside 32 entries and `&pBurst->data_buf[i * 6]` stays inside the 192-byte array (highest write is 186..191).

The problem is what it reports. The loop breaks on tail `0x01` — "last valid point of this batch" — and sets `status = LH001_91_FIFO_READ_OK` while `count` may be well below `expected_count`:

```c
if (pBurst->frames[i].tail == 0x01) {
    pBurst->status = LH001_91_FIFO_READ_OK;
    break;
}
```

The application's gate is status plus master/slave count equality:

```c
if ((master_burst.status == LH001_91_FIFO_READ_OK) &&
    (slave_burst.status == LH001_91_FIFO_READ_OK) &&
    (master_burst.count == slave_burst.count))
```

Never that `count == LH001_91_FIFO_THRESHOLD`. It then copies a fixed block:

```c
uint16_t block_size = LH001_91_FIFO_THRESHOLD * SAMPLE_BYTES; // 150
memcpy(&UartTxBuffer[Write_Index][0], master_burst.data_buf, block_size);
memcpy(&UartTxBuffer[Write_Index][block_size], slave_burst.data_buf, block_size);
```

If both chips return 15 frames with a tail marker, 90 bytes are real and 60 are the zeros left by the `memset` at function entry. This stays in bounds — `data_buf` is 192 bytes and the read is 150 — so there is no memory-safety fault, and that is what makes it dangerous: the downstream consumer receives 25 well-formed samples per chip per packet, 10 of them fabricated zeros, with `fifo_ok_count` incrementing as if nothing happened. Silent zero injection into an acquisition stream is worse than a dropped packet.

The related gap is `LH001_91_FIFO_READ_NO_TAIL`. It exists in the enum and in `fifo_status_str`, but nothing assigns it. The case it names — the loop runs the full `expected_count` and never sees a terminating tail, meaning the reader and the chip's FIFO pointer disagree — currently reports `OK`.

`lh001_91_read_fifo_burst_dual` calls the `_num` variant with `LH001_91_FIFO_MAX_DEPTH` (32) rather than the configured threshold (25). It is unused by the application, but it will over-read by 7 frames if called.

## Double-buffer producer/consumer desync

One producer (main loop, FIFO path) and one consumer (main loop, UART path) share `UartTxBuffer[2][300]`, with `Write_Index`/`Read_Index` toggled by XOR and `Data_Ready_Flag`/`Uart_Tx_Busy` as handshakes. Two distinct defects break it.

The producer never checks whether the block it is about to replace was consumed:

```c
Write_Index ^= 1;
Data_Ready_Flag = 1;
```

If the consumer has not yet picked up the previous block, `Data_Ready_Flag` was already 1 and that block is lost with no counter incremented. The code tracks `fifo_ok_count`, `fifo_error_count`, `fifo_recovery_count` and `fifo_reentry_drop_count`, but has no equivalent for a buffer overrun, so this loss is invisible.

The more serious defect is asymmetric index advancement. On the error path the `memcpy` and `Write_Index ^= 1` are both skipped, but `Read_Index ^= 1` in the consumer runs unconditionally at transmit start. After a single read error the two indices are offset by one for the remainder of the run, and the consumer transmits the same buffer the producer is filling. The UART sends a 300-byte block that is half old and half new, torn at whatever byte the producer had reached, and every subsequent packet is torn the same way. The error path also clears `Data_Ready_Flag` unconditionally, discarding a block that may already have been staged.

The transmit start ignores the HAL return:

```c
HAL_UART_Transmit_IT(&huart2, UartTxBuffer[Read_Index], BUFFER_SIZE);
```

`Uart_Tx_Busy` was set to 1 immediately before. If this returns `HAL_BUSY` or `HAL_ERROR`, no transfer starts, `HAL_UART_TxCpltCallback` never fires, and `Uart_Tx_Busy` stays 1 for the lifetime of the program — transmission stops permanently while the FIFO path keeps running and keeps overwriting buffers.

This whole path is compiled out in the current configuration: `USE_ASCII_CODE_PRINT` is 1, which selects the `printf` branch, and `#if !USE_ASCII_CODE_PRINT` excludes the UART scheduler. The defects are latent until binary mode is enabled.

## SPI error handling collapses into data

The port layer's single primitive:

```c
static inline uint8_t stm_lh_spi_txrx8bit(uint8_t tx_byte)
{
    uint8_t rx_byte = 0;
    if (HAL_SPI_TransmitReceive(&hspi1, &tx_byte, &rx_byte, 1, 5) != HAL_OK)
    {
        return 0xFF; // 出错或超时返回 0xFF
    }
    return rx_byte;
}
```

`0xFF` is a legal value for every register and every sample byte in this device, so a bus timeout is indistinguishable from real data, and every read in the driver funnels through here. In a register read it produces a plausible-looking configuration value. In a FIFO frame it produces `tail = 0x03`, which the burst reader interprets as a chip-side FIFO overflow and reports as `LH001_91_FIFO_READ_OVERFLOW` — the application then runs `fifo_recover()` against a chip that never overflowed, misattributing a bus fault to the device.

The 5 ms timeout is long relative to a few-microsecond byte transfer, so it will only fire on genuine bus trouble — precisely the case being swallowed.

The transaction structure matters for throughput and for how often this error path is exposed. Every byte is a separate `HAL_SPI_TransmitReceive` call, which on the H7 reconfigures `TSIZE` and toggles `SPE` per call. One 48-bit frame costs 7 such calls plus two 10 µs delays; a 25-frame burst across two chips is 350 calls and roughly 1 ms of delay alone. That works at the current 1 kHz data rate but leaves little headroom, and it means 350 independent opportunities per burst for a silent `0xFF`.

## ISR/main-loop concurrency

`HAL_GPIO_EXTI_Callback` does no SPI work, no `HAL_Delay`, and no busy-waiting. The `DRDY1` branch increments a counter and sets a flag:

```c
drdy1_irq_count++;
if (fifo_irq_pending == 0) {
    fifo_irq_pending = 1;
} else {
    fifo_reentry_drop_count++;
}
```

All variables crossing the ISR boundary — `fifo_irq_pending`, `drdy1_irq_count`, `fifo_reentry_drop_count`, `Write_Index`, `Read_Index`, `Data_Ready_Flag`, `Uart_Tx_Busy` — are `volatile`, each has a single writer, and all are single-byte or naturally-aligned 32-bit. The read-modify-write and torn-read hazards do not arise here and no critical section is missing. `master_burst`/`slave_burst` are touched only from the main loop.

`LH001_91_DELAY_10US` busy-waits on `TIM17->CNT` with a bounded `timeout` counter, and `HAL_Delay` appears only in `lh001_91_hw_reset` during startup. Neither runs in interrupt context. The `fifo_reentry_drop_count` counter shows the overrun case was considered at the ISR boundary; the gap is that the same care was not applied at the buffer boundary.

The `lh001_91_wakeup` busy-wait `for (uint32_t i = 0; i < 100; i++);` is a compiler-removable empty loop rather than a reliable delay, but that function is unused here.

## Register access and decode

Read-modify-write is applied on `SPICTRL`, `INTOEN`, `FIFOSTA`, `CONFIG1`, `BUFCON`, `MODCLK`, `LOCON2`, `LOCON3` and `PGACTRL1`, each masked with the matching `MSK_` constant before the field is or-ed in. I checked every mask and position pair against the header definitions and found no mismatches. `PGACTRL` and `LOCON1` are written blind, defensible since the struct fields specify every bit those registers use, though it does clear `PGACTRL`'s `RESET` bit as a side effect.

`lh001_91_fifo_setup_dual` clears `DCMODE` with a raw literal where the named constant exists:

```c
val &= ~(1U << 2);   /* MSK_LH001_91_SPICTRL_DCMODE is defined as 0x04 */
```

`thresh_num` is unvalidated. The threshold is written as `(cnt_val & MSK_LH001_91_FIFOSTA_ENOUGHCNT)` with a 5-bit mask, so a caller passing 40 gets `39 & 0x1F == 7` — a threshold of 8 rather than 40, with no indication. The current call site passes 25.

The FIFO frame decode is arithmetically correct: the 24-bit sample is assembled as bits 23-22 from `dat[2] & 0x03`, 21-14 from `dat[3]`, 13-6 from `dat[4]`, 5-0 from `dat[5] >> 2`, with `tail` in the low two bits of `dat[5]`, consistent with a 48-bit frame carrying a 2-bit tail. The non-FIFO decode uses the same layout without the tail shift.

One mask defect appears in both decoders:

```c
pData->gpio      = (dat[1] >> 4) & 0x03;
pData->reserved1 = ((dat[1] & 0x1F) << 8) | ...;
```

`gpio` takes bits 5-4 of `dat[1]`, so `reserved1` should mask `0x0F`, not `0x1F` — bit 4 is counted twice. No consumer reads `reserved1`, so this is cosmetic today, but it will mislead anyone who later uses the field.

`lh001_91_adc_code2mv` sign-extends correctly and uses single-precision literals throughout to avoid double promotion:

```c
rlt = (float)dat * 2.0f * (float)ref / (6.0f * 16777215.0f);
```

The `6.0f` is the PGA gain, hardcoded. The current configuration is `ENUM_LH001_91_PGA_PGAGAIN_6` so the number is right, but nothing ties the two together — changing `pga_init.gain` silently produces wrong millivolts from a function whose entire purpose is returning a physical unit. Gain belongs in the signature alongside `ref`.

`lh001_91_hw_reset` writes raw opcodes for the sequence that unlocks and clocks both chips:

```c
LH001_91_SpiTxRxByte(0x5E); // WREG to USERKEY (0x1E)
LH001_91_SpiTxRxByte(0x00);
LH001_91_SpiTxRxByte(0x86); // unlock key
```

`0x5E` is `SPI_CMD_WREG_MSK | ADDR_LH001_91_USERKEY`, `0x86` is `LH001_91_USERKEY`, `0x56` is `SPI_CMD_WREG_MSK | ADDR_LH001_91_CLKCON`. All three constants are already in the header. The comments explain the timing requirements well, but the literals will drift from the constants under maintenance.

## Recovery path

```c
lh001_91_reset_fifo_cmd();   /* SPI_CMD_RST_FIFO to master and slave */
lh001_91_reset_fifo_hw();    /* stop -> 10us -> go */
```

With `ADC_CONV_START_HW == 1`, `lh001_91_adc_stop` and `lh001_91_adc_go` drive the single shared `Start_Pin`, so `lh001_91_reset_fifo_hw` stops and restarts conversion on both chips regardless of which one had the error. That may be desirable for keeping the two chips sample-aligned, but it is a side effect the function name does not convey, and `lh001_91_adc_stop_dual(chip_id)` behaves the same way — the `chip_id` parameter is ignored entirely in the hardware-start configuration.

Recovery does not clear `fifo_irq_pending`, so an edge that arrived during recovery is serviced immediately afterward against a just-reset FIFO. It also does not read or clear `FIFOSTA`, so a chip-side `FULL` or `OVERFLOW` flag survives the recovery.

## API surface and header hygiene

`LH001_91.h` has a proper include guard and uses fixed-width types throughout. The `_dual` functions with single-chip convenience macros are a clean way to extend a single-chip driver to two chips without breaking existing call sites.

The gaps follow from the error-reporting problem: every register, init, and command function returns `void`, so `lh001_91_read_regs_dual` cannot report that it read nothing and `lh001_91_adc_init_dual` cannot report that the chip did not accept the configuration. The FIFO burst reader is the only function with a status channel, via its struct field.

Two functions are defined in `LH001_91.c` but never declared in the header: `lh001_91_Isource_cfg` (documented with a full comment block, so it is intended as API) and `fifo_setup` (non-static and unprefixed, so it also pollutes the global namespace). `fifo_print_counters` and `UART_SendString` in `main.c` are never called — `fifo_print_counters` is the only consumer of `drdy1_irq_count` and `fifo_reentry_drop_count`, so those counters are accumulated and never observed.

`const` is missing where the intent is read-only: `pRegs` on `lh001_91_write_regs_dual`, and the `pInit` pointers on `lh001_91_adc_init_dual`, `lh001_91_pga_init_dual`, `lh001_91_leadoff_init_dual`. `REG_DUMP_t.reg_name` is `uint8_t[48]` for what is clearly a string and should be `char`; `lh001_91_reg_dump` never populates it.

`lh001_91_port.h` is the porting layer but includes `stm32h7xx_hal.h` and `main.h` and references `htim17`/`hspi1` directly, so the driver cannot move to another MCU without editing it. `LH001_91.h` uses `#include "stdint.h"` where `<stdint.h>` is correct.

`ADC_DATA_FIFO_t` and `ADC_DATA_NOFIFO_t` declare `volatile uint64_t` bitfields with a 48-bit `reserved0` padding member. These are plain RAM structures filled by the decoder, not memory-mapped registers, so `volatile` forces a re-read from memory on every field access for no benefit. The `reserved0` padding pushes each frame to 16 bytes, so `frames[32]` costs 512 bytes rather than 256 in every `LH001_91_FIFO_BURST_t`, and there are two of those plus the 300-byte UART buffer.

## Cache coherency, DMA, and MPU

Checked and not applicable. There is no DMA anywhere in the project code — `HAL_DMA_Init` appears only in the vendor HAL sources and no `DMA_HandleTypeDef` is declared; all SPI and UART traffic is polled or interrupt-driven. Neither `SCB_EnableDCache` nor `SCB_EnableICache` is called, so caches are off and the classic H7 D-cache/DMA corruption mode cannot occur. `MPU_Config` is the standard CubeMX background region: a 4 GB `NO_ACCESS` region 0 with `SubRegionDisable = 0x87` releasing the low 1.5 GB (flash, SRAM, peripherals) and the top 512 MB to the default memory map.

If DMA is added later for the SPI burst — the natural fix for the 350-call-per-burst structure — the buffers will need placement in a non-cacheable region or explicit cache maintenance, and `LH001_91_FIFO_BURST_t` will need 32-byte alignment.

## Peripheral init and fault handling

Mostly CubeMX-generated, weighted accordingly.

`MX_SPI1_Init` uses CPOL low / CPHA 2-edge with `SPI_NSS_SOFT`, matching the device and the driver's `SOFTWARE_SPI_CS` path. `MX_TIM17_Init` sets `Prescaler = 0`, and the hand-written `LH001_91_DELAY_INIT` recomputes it from `HAL_RCC_GetPCLK2Freq()` with the APB2 doubler check, then forces the value in with an `EGR` update event and clears the resulting flag — necessary given the generated prescaler of 0. Resetting `CNT` without resetting the prescaler counter means the first tick lands anywhere within one microsecond, so the delay is 10–11 µs rather than exactly 10, which is the safe direction for a minimum-width requirement.

`MX_USART2_UART_Init` runs at 2 Mbaud with FIFO mode explicitly disabled. The NVIC enable for USART2 sits in a `USER CODE` block in the MSP init, hand-added, and is required for the `_IT` transmit path. EXTI lines are at preemption priority 0 and USART2 at 1, so a DRDY edge can preempt the UART ISR; the DRDY handler is short enough that this does not matter.

`fputc` transmits one character per `HAL_UART_Transmit` call with a 2 ms timeout and an unchecked return, so `printf` output can drop characters silently under contention. In the current ASCII configuration an `[ADC CODE]` line is roughly 45 such calls every fifth burst.

`Error_Handler` disables interrupts and spins, and the fault handlers are bare infinite loops. This is generated code, but for an unattended acquisition device the consequence is that any HAL init failure or fault bricks it silently with no external indication and no reset. An LED is available on PA15, and no watchdog is configured.

## Assessment

Not ready to rely on for data acquisition. The reason is not code quality in the ordinary sense — the register handling is careful, the masks and decode arithmetic check out, and the ISR/main-loop concurrency design is correct where a lot of hand-written firmware is not. The problem is that the FIFO data path can produce output that looks valid and is not. A short burst is padded with zeros and counted as a success; an SPI timeout becomes the byte `0xFF` and is either accepted as a register value or misread as a chip-side FIFO overflow; and once binary transmit mode is enabled, a single read error permanently offsets the double-buffer indices so every packet after it is torn. None of these announce themselves, which is what makes them worse than a crash.

Layered on top is the trigger question. The driver configures the chip to interrupt on FIFO threshold while the application listens on data-ready, with the two INT handlers enabled and empty, and nothing ever clears `FIFOSTA` — which on a level-asserted output would stop acquisition after the first burst. I could not settle this from the code alone; it depends on the schematic. Until it is settled, observed behaviour of the FIFO path cannot be interpreted with confidence, because a wrong-pin trigger and a working-but-buggy reader look similar from the outside.

Top three to fix first:

1. **Resolve the interrupt routing, then clear `FIFOSTA` after every burst.** Confirm against the schematic which MCU pin carries the chip's ENOUGH output. If it is INT1/INT2, move the trigger there and drop the empty handlers; if the intent really is per-conversion DRDY, then FIFO mode and its threshold are the wrong mechanism. Either way, read and clear `FIFOSTA` at the end of each burst so the interrupt can re-arm and the chip's own `FULL`/`OVERFLOW` bits become visible.

2. **Make partial and failed reads impossible to mistake for good data.** Require `count == LH001_91_FIFO_THRESHOLD` before staging a block, or copy `count * SAMPLE_BYTES` instead of a fixed 150; assign `NO_TAIL` when a burst completes without a tail marker; set `BAD_ARG` into the struct before the early return so a rejected call cannot return the previous call's frames.

3. **Give the SPI layer an out-of-band error channel.** Stop mapping `HAL_SPI_TransmitReceive` failure to `0xFF`, and return status from at least `lh001_91_read_regs_dual` and `lh001_91_write_regs_dual` so init failures and bus faults surface instead of propagating as plausible data. This is also what lets the recovery path distinguish a real chip overflow from a bus timeout, rather than resetting a healthy device.

Then, before enabling binary transmit mode: fix the `Write_Index`/`Read_Index` asymmetry on the error path, add an overrun counter for the `Data_Ready_Flag`-already-set case, and check the `HAL_UART_Transmit_IT` return so a `HAL_BUSY` cannot latch `Uart_Tx_Busy` forever.
